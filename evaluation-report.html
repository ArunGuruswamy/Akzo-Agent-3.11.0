Remaining steps

  1. Set each target repository's local path in %USERPROFILE%\.akzo-agent\repos.json.
  2. Run the agent's investigation; it records the repository's Sonar configuration files, pipeline Sonar step, analyzer settings, and coverage settings with paths.
  3. Get the analysis from the repository's own route: push the change branch and open a pull request so the pipeline's Sonar step runs, or, with authorization, run the scanner command the repository documents, using a token from your own secret store (never committed).
  4. From the SonarQube/SonarCloud project page or Web API for that commit, copy the gate result, new-code issues, security findings, duplication, and new-code coverage into the record above.
  5. Fix valid findings in code. If a finding seems wrong, record the reasoning and let the rule owner decide; do not suppress it.

Design

  • Arms: A = regular GitHub Copilot (built-in Agent) with the same requirement text, acceptance criteria, and a list of the same relevant files. B = the akzo-master-sdd custom agent.
  • Tasks (chosen by a facilitator from a real Akzo repository before any run, with acceptance criteria written in advance): T1 a bounded defect fix with a reproducible failure; T2 a small API feature (one field or endpoint, with validation and tests).
  • Controls: same starting commit, IDE and version, model, permissions and tool settings, dependencies restored in advance, same acceptance criteria and done definition.
  • Runs: at least 3 per arm per task (5 preferred), alternating which arm runs first. Record the first akzo-master-sdd run after installation separately as cold start (registry setup, first investigation, optional graph build).

Procedure for one run

  1. Create an isolated checkout without touching the reference repository's own .git: 
    git clone --quiet "<reference repo path>" "$env:USERPROFILE\.akzo-agent\benchmark\<task>-<arm>-<run>"
git -C "$env:USERPROFILE\.akzo-agent\benchmark\<task>-<arm>-<run>" checkout --detach <start commit>
  2. For arm B, point the registry entry's path at that checkout (and restore it afterwards).
  3. Open the checkout in the IDE, select the arm's agent and model, and start a stopwatch with the first prompt.
  4. Log a timestamp at each phase change: investigation, spec/plan (arm B includes writing spec.md and plan.md), implementation, validation. Separately log active human time (typing, reading, answering, approving).
  5. Count clarification rounds, correction rounds (human-requested fixes), build attempts, and test attempts.
  6. Stop when the arm declares done or after a fixed time box (e.g. 90 minutes); mark incomplete runs as not completed.
  7. A reviewer who did not run the session, blinded to the arm where practical, scores acceptance criteria and records defects. Run the repository's tests, coverage, and Sonar route on the result.
  8. Record tokens only from reliable product telemetry; otherwise write NOT AVAILABLE. Tool calls and files read may be recorded as labeled proxies only.
  9. Append one row per run to benchmark\results-template.csv (copy it first).

Analysis rules

  • Compare only completed runs that satisfy all acceptance criteria. Report per arm and task: n, median, and min-max of total elapsed and active human time; the cold start reported on its own.
  • Report differences with n and spread. With fewer than 3 comparable runs per arm, report raw values only and draw no conclusion.
  • Include spec/plan documentation time in arm B totals. Never convert proxies into token or cost figures.
