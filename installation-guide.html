  • Windows account without admin rights is fine. Windows PowerShell 5.1 (built in) runs the scripts.
  • Git on PATH (the agent inspects repository state).
  • A GitHub Copilot subscription, signed in inside the IDE.
  • Optional: Python with graphify for code graphs. Without it the agent uses targeted search.

Activation and isolation

The Akzo workflow runs only when you select akzo-master-sdd. Regular Copilot Chat, Ask/Plan/Agent, and your other custom agents keep their normal behavior.

How it is done

  • One discovered file. The agent file is the only Akzo file placed where Copilot discovers customizations. It is used when you pick it; it is not an instruction file applied to every chat.
  • The whole workflow is inside the agent file. Intake, investigation, spec, plan, implementation, validation, and review rules load only with akzo-master-sdd, and no workflow files are read at run time. The helper script and spec/plan templates sit in %USERPROFILE%\.akzo-agent\modules\, a folder neither IDE scans.
  • Why not skills: VS Code adds every discovered skill's name and description to each agent's prompt (verified in the VS Code 1.136.1 source; only skills marked disable-model-invocation are skipped, and those still appear in the / menu). Visual Studio documents skills as something "any agent can discover and use automatically". Neither IDE documents restricting a skill to one agent.
  • No subagent use (VS Code). The VS Code copy sets disable-model-invocation: true, which VS Code documents as preventing other agents from invoking it as a subagent. Visual Studio does not document subagent invocation of custom agents, so its copy keeps only the documented fields (name, description).
  • Never in Copilot memory. VS Code stores Copilot "memories" in %APPDATA%\Code\User\globalStorage\github.copilot-chat\memory-tool\memories\ and loads the first 200 lines of user memory into every agent (Copilot Chat 0.70 source). The agent is told never to write its rules there; install.ps1 -Verify reports memory files that mention Akzo as LEAK, and Repair (-CleanMemory) removes them after a backup. This is how one agent's instructions reach other agents.
  • Same chat, different agent. Switching the agent inside one chat keeps the conversation history, so the new agent still sees the earlier Akzo messages. Start a new chat for other work.
  • No global instructions. Nothing is written to AGENTS.md, .github/copilot-instructions.md, ~/.copilot/instructions, any repository, or VS Code/Visual Studio settings. Existing agents and skills are not changed or disabled.

-ConfigureVSCode adds read access to the Akzo folders and an auto-approve rule for the helper command (see Permissions). Read access lets any Copilot agent read those folders without asking; it does not load anything into other agents.

Install

One click (recommended)

  1. Double-click Install-MasterAgent.cmd in the Akzo-Agent folder.
  2. Click Add Repository…, type or paste the path of your local clone (Ctrl+V; quotes from File Explorer's Copy as path are removed; spaces and \\server\share paths work) or click Browse…, then Validate and Save. The name is suggested from the folder. Repeat for each repository.
  3. Click Install / Upgrade. The log shows every file written, backed up, or removed, and ends with == Install finished OK ==; the Agent Installation Status panel then shows each check.
  4. Restart VS Code / Visual Studio 2026.

The same window has Repair (restore missing or edited files, clean leaked Akzo text from Copilot memory; it then lists what is still unresolved), Verify Installation, and Uninstall. Install and Repair are idempotent: running them again never creates a second agent. If a write fails, every file changed in that run is restored (rollback).

Repositories table (name, path, validation, agent status): Edit… (or double-click / Enter) changes the name or path, Remove (or Delete) asks first and removes only the registration, Open in Explorer, Validate, Refresh. Changes are saved to repos.json at once (backed up first). The folder, its Git repository, and your files are never deleted. Changing a repository's path, or removing it, withdraws the authorization you recorded for it, so the agent asks again for the new folder. A folder that is not a Git repository can be saved after a warning, but the agent works only on Git clones.

Agent Installation Status shows Verified, Warning, Failed, Not Applicable, or Not Checked for: agent files, agent metadata (front matter a strict YAML parser accepts), VS Code and Visual Studio configuration (the installed IDE versions and settings), old-version conflicts, helper and skills, repositories, version consistency, and configuration integrity. Whether the agent appears in the IDE's picker is always Not Checked: it cannot be read from outside the IDE, so the panel gives the manual steps.

From PowerShell

Open PowerShell in the Akzo-Agent folder (the folder that contains scripts\install.ps1). No downloads happen; files are copied from this folder.

1. Preview

powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\install.ps1 -DryRun

2. Install (or update)

powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\install.ps1

Add -ConfigureVSCode to cut VS Code permission prompts (see Permissions):

powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\install.ps1 -ConfigureVSCode

Writes the agent to both user agent folders, the helper and templates to %USERPROFILE%\.akzo-agent\modules, creates %USERPROFILE%\.akzo-agent\repos.json if it does not exist, and creates the tasks folder where refined PBIs go (it prints the exact path). It validates repos.json and changes it only for Add repository / -AddRepo (backed up first); it stops without changes if the file is not valid JSON. Any file it replaces is backed up first to %USERPROFILE%\.akzo-agent\backups\<timestamp>\. Safe to re-run.

3. Verify the files

powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\install.ps1 -Verify

Checks installed files against the SHA-256 manifest, checks that no Akzo skill sits in a shared skill folder, and lists registered repositories. It ends with one CHECK [status] name: detail line per item (the setup window shows them). It cannot check the IDE's agent picker; do that in the IDE sections below.

Agent not in the Copilot agent picker

  1. Run Verify Installation and fix every Failed row; each names its fix.
  2. VS Code: the agent is read from %USERPROFILE%\.copilot\agents (default of chat.agentFilesLocations in the VS Code builds the check finds). Reload the window, then Ctrl+Shift+P > Configure Custom Agents… lists every agent VS Code found. A user setting that turns ~/.copilot/agents off, or chat.disableAIFeatures, hides it.
  3. Visual Studio: 2022 (17.x) has no custom agents; 2026 reads %USERPROFILE%\.github\agents from 18.5. The .github\agents copy is for Visual Studio only; VS Code reads .github/agents only inside an open workspace.
  4. Agents are per user: nothing needs to be installed into each repository. Install as the Windows user who runs the IDE.
  5. An organization Copilot policy can turn custom agents off; ask your administrator if the files and settings are verified and the agent is still missing.

package integrity: NOT VERIFIED - development working copy means the files came from a Git clone or a source download, which has no release-manifest.json. Install from the release zip (release\<version>-rc1\) to have every file checked against the release manifest before anything is written.

Upgrading from 2.x: the second agent akzo-sdd is removed (from the manifest, or when an Akzo agent file of that name is found without one), after a backup. A file of that name with other content is left alone.

If an earlier version put akzo-* skills in %USERPROFILE%\.copilot\skills, the installer backs them up and removes them.

Only one IDE

powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\install.ps1 -Target VSCode
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\install.ps1 -Target VisualStudio

-Target describes what should be installed after the run: switching from the default (All) to one IDE removes the other IDE's agent file. Later runs without -Target or -VisualStudioAgentsDir keep your last choice; pass them again to change it. The helper and templates are always installed.

-ExecutionPolicy Bypass applies only to that one process; it does not change your machine policy.

VS Code setup

  1. Run the installer, then restart VS Code (or run Developer: Reload Window).
  2. Open the Chat view. Keep the session target on Local (the default).
  3. Open the Agent dropdown and select akzo-master-sdd. It stays selected until you switch.
  4. If you did not install with -ConfigureVSCode, expect the prompts listed in Permissions.

VS Code settings change only with Configure VS Code in the setup window (on by default) or -ConfigureVSCode, inside a marked block that Uninstall removes. The default chat.agentFilesLocations already includes ~/.copilot/agents. Nothing Akzo-specific appears in the / menu.

Visual Studio 2026 setup

  1. Check Help > About: Visual Studio 2026 version 18.5 or later (user-level agents arrived in 18.5; 18.4 reads agents only from a repository's .github/agents). Visual Studio 2022 does not support custom agents.
  2. If you changed the user agents folder in Tools > Options > GitHub > Copilot, install with that folder: 
    powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\install.ps1 -VisualStudioAgentsDir "D:\MyAgents"
    Replace D:\MyAgents with the folder shown in that options page.
  3. Restart Visual Studio and open Copilot Chat (GitHub Copilot badge > Open Chat).
  4. Open the agent picker and select akzo-master-sdd, or type @akzo-master-sdd in the chat input.
  5. Open the Tools panel and make sure search, file reading/editing, and terminal tools are enabled. Microsoft documents that tool groups can start disabled for custom agents. The agent needs the terminal for its helper and file reading/editing for the task.

Configure reference repositories

Easiest: Install-MasterAgent.cmd > Add repository… (or install.ps1 -AddRepo "C:\src\my-repo"). It adds the clone with its folder name as id and uses an existing spec folder (openspec/changes, src/.github/specs, .github/specs, docs/specs, specs) as specsDir. Or edit %USERPROFILE%\.akzo-agent\repos.json and set path to each local clone. This file stays on your machine; it is never written into any repository.

notepad "$env:USERPROFILE\.akzo-agent\repos.json"

Each entry has id, path, purpose, stack, notes (hypotheses until verified), commands (build, test, codegen, lint), verified (date and commit), and optionally specsDir (see Start a task). The agent fills commands once it has actually run them. Check the registry:

powershell -NoProfile -ExecutionPolicy Bypass -File "$env:USERPROFILE\.akzo-agent\modules\investigate\scripts\akzo.ps1" registry

Tasks folder: to keep refined PBIs somewhere else, set "tasksDir" at the top of repos.json to an absolute path outside any Git repository (environment variables allowed, e.g. "%USERPROFILE%\\Documents\\Akzo-SDD\\tasks"), then re-run the installer to create it. Empty means the default. install.ps1 -Verify reports a tasksDir that is relative or inside a repository, and duplicate or unusable repo ids.

Opening a folder in the IDE does not make it the target. The agent picks one implementation target from the registry and treats other repositories as read-only references unless you authorize changes there.

Corporate security (G8): authorization and policy

From 3.4.0 the agent does not index, extract documents from, or output content of a repository until that repository is authorized. This is checked by the helper, not only by the agent's instructions. The G8 gate at the end of every task (all modes) is mandatory and cannot be waived.

Developer: authorize a repository

On first use the agent asks whether you hold an authorization to process the repository with this IDE and model, and for its reference and data classification, then records your answer. You can also do it yourself (the IDE asks you to confirm this command; it is never auto-approved):

powershell -NoProfile -ExecutionPolicy Bypass -File "$env:USERPROFILE\.akzo-agent\modules\investigate\scripts\akzo.ps1" authorize -Repo <repo-id> -Reference "<approval you hold>" -Classification internal -Model "<model in use>" -Hosts "<sonar host>"
powershell -NoProfile -ExecutionPolicy Bypass -File "$env:USERPROFILE\.akzo-agent\modules\investigate\scripts\akzo.ps1" policy -Repo <repo-id>

This is your own statement, stored with your user name. G8 reports it as NOT VERIFIED: it is not corporate approval. Restricted data cannot be authorized this way.

Administrator: policy file

A policy.json at %ProgramData%\AkzoAgent\policy.json (or the path in the AKZO_AGENT_MACHINE_POLICY environment variable) is used when it exists; only when there is none, a per-user copy in %USERPROFILE%\.akzo-agent is read. It counts as administrator-managed only when the current user cannot write it, so protect the file with administrator-only write access.

{
  "schemaVersion": 1,
  "reference": "ISMS-AI-7",
  "allowDeveloperAttestation": true,
  "approvedModels": ["Model A"],
  "allowedHosts": ["sonarqube.example.com"],
  "defaults": { "classification": "internal", "memory": "allowed", "retentionDays": 180 },
  "repositories": {
    "orders-api": { "authorized": true, "reference": "CHG-1234", "classification": "confidential", "memory": "allowed", "retentionDays": 90 },
    "payroll":    { "authorized": false, "reason": "AI processing not approved" }
  }
}
  • authorized: false blocks the repository (BLOCKED_BY_POLICY); an unreadable policy blocks everything (fail closed).
  • allowDeveloperAttestation: false means only repositories listed here are processed.
  • approvedModels: a model the developer states that is not listed blocks processing. The helper cannot see which model Copilot actually uses; it checks what is stated.
  • allowedHosts: the only hosts the helper may call (read-only Sonar queries).
  • memory: "disabled" refuses new facts; retentionDays expires facts older than that.
Known limitation: the developer's authorization is not technically protected. It is stored in %USERPROFILE%\.akzo-agent\authorizations.json. Any process running as you, including a model with file-edit or terminal tools, can write that file directly; the authorize command asks the IDE for confirmation, but the helper cannot tell it from a direct write. Your approval is therefore enforced by the IDE's prompts and the agent's instructions, and instructions alone do not enforce approval. Where approval must be enforced, an administrator places a policy.json that users cannot write, with "allowDeveloperAttestation": false: developer statements are then ignored and only the listed repositories are processed. G8 reports a developer statement as NOT VERIFIED in every case.

Commands, gate, report, purge

  • The agent runs guard before each non-helper terminal command: ALLOW, NEEDS_APPROVAL (asks you), or BLOCK (never run; no approval releases it). The guard is run by the agent; the IDE cannot force it, so the command log shows what the agent reported.
  • security -Id <PBI> evaluates 13 controls and writes <tasks>\<repo>\<PBI>\evidence\corporate-security-report.html. FAIL blocks the handover, NOT VERIFIED allows DONE_WITH_CONCERNS at best, only PASS allows DONE. Never edit the log, the report, or the policy to change an outcome.
  • purge -Repo <repo-id> -Confirmed [-IncludeTasks] deletes a repository's memory (and optionally its task folders); the IDE asks you to confirm.
  • Memory and task folders are restricted to your account, SYSTEM, and Administrators. They are not encrypted; keep tasksDir out of synchronized folders.

Package report with the controls, test evidence, endpoint-protection findings during development, limitations, and required approvals: corporate-security-report.html in the package. Deployment in an organization still needs those approvals.

Fresh tasks, branches, modify and resume

  • Start Development, New Development, or Start Implementation always starts a fresh task: the file dialog for the refined PBI, then the optional dialog for supporting documents. It never resumes the previous PBI. If the dialog cannot open, the agent reports the error and offers a file path or Start-Development.cmd instead; it never skips intake.
  • When a request is unclear, the agent asks once: a) start new development, b) modify an existing implementation, c) resume an existing PBI. resume <PBI> and modify <PBI> go straight to that task.
  • Branch: before any file is created or code changed, the agent shows repository, branch, HEAD, and uncommitted changes, and asks: a) create a new feature branch (feature/<id>-<title>, lowercase with hyphens; recommended on main/develop or a branch that belongs to another PBI; you confirm the base branch), b) continue on the current branch, c) select an existing branch. Creating or switching a branch always asks for your confirmation in the IDE. Nothing is stashed, reset, or discarded; switching with uncommitted changes needs your agreement (git carries them along and refuses if they would be overwritten).
  • Specs: one folder per work item, <specsDir>\<id>-<title>\spec.md and plan.md. Another PBI's folder is never reused (SPEC_LOCATION_TAKEN); resuming on a branch that lacks the PBI's spec stops with WRONG_BRANCH.
  • Modify: the current spec, plan, PBI, inputs, and statuses are copied to <task>\history\ first; then the changed parts go through the gates again.
  • Upgrading from 3.4.x: existing tasks resume with their specs and approvals; for tasks without a recorded branch decision the agent reports that and asks before changing code.

Repository profiles: DAB and CDMS

The agent identifies the repository before it reads code for a change, and loads only that repository's rules. The helper decides from the solution file, never from feature names:

  • The other profile's files are never loaded, and a dotnet command naming another repository's solution is refused by the command guard.
  • Before handover the agent runs the pre-PR review on the branch. It reports the six recorded PR review findings: validation-exception conversion in PUT and POST functions that the middleware already handles, duplicate changes, a validator off the FluentValidation pattern, misplaced command or query dependencies, and missing or outdated XML documentation. It also reports the CDMS 200-character line limit and broad catches. Errors must be fixed before Ready.
  • Your team's own rule files: save them under %USERPROFILE%\.akzo-agent\profiles-custom\ with the same relative path as the shipped file, for example profiles-custom\instructions\cdms\sonar-rules.instructions.md. The agent then uses yours; upgrades never change that folder. Install-MasterAgent.cmd > Verify (or install.ps1 -Verify) lists how many profile files are installed and how many custom files you have.
  • Only what the request needs (3.7.0): the agent passes the request to profile -Query. It loads the shared skills, the profile's core skills, the Sonar rules, and the skills that match the request (for example FluentValidation for a validator change). The rest is listed as deferred and read when the work reaches it. A new shared skill, business rule branch coverage, checks every approved rule path by path. Detection is cached per repository and refreshed after any commit, checkout, or edit. The cache lives in maps\<repo>\profile-detection.json and is safe to delete.
  • Staged tests (3.7.0): affected -Repo <id> [-Base main] tells the agent which projects to build and which tests to run after each edit (focused, then dependent test projects). The full suite with coverage runs once, at the final gate. Changes to the solution, props, or package files always mean the full build and suite.
  • Start menu (3.8.0): say start and choose 1 Fix Issue, 2 Refactor Existing Code, 3 New Development / PBI, 4 Review / Analyze Only, or 5 Custom Task. A Sonar finding, error, failing test, PR comment, or PBI given directly is routed without the menu. Fix Issue and Refactor read only the affected code, its tests, and the Sonar rules (profile -Task fix), skip the PBI, spec, and plan, and end with Issue / Cause / Fix / Verification / Status.
  • Why Copilot reads documents you did not ask for (3.8.0): guidance -Repo <id> lists the repository's instruction files, when the IDE adds each one, and every document they tell Copilot to read. copilot-instructions.md, a root AGENTS.md or CLAUDE.md, and applyTo: '**' instructions reach every request of every agent; move document-reading rules into scoped .instructions.md files or skills. The command never edits them.
  • Review-only or plan-first requests ("review this and propose a fix before changing anything") end with the analysis and proposed changes. Nothing is edited until you approve.
  • Chat requests: Implement this requirement, Fix PR comments, Review changes, Run tests. Results are reported as Ready, Ready with Warnings (something could not be verified, for example SonarCloud), or Not Ready.

Repository memory, retrieval, and Auto Mode

  • Memory lives in %USERPROFILE%\.akzo-agent\maps\<repo-id>\ (architecture.json, component-index.tsv, symbols.tsv, facts.json, memory-log.tsv). Edits are noticed by content, committed or not; only changed files are re-read. A stale fact must be revalidated before use; facts expire with their evidence. Corrupt files are renamed *.corrupt-<time> and rebuilt.
  • Retrieval: context -Query "<terms>" -Mode compact|balanced|deep. Defaults and budgets can be set in repos.json: "retrieval": { "mode": "balanced", "budgets": { "compact": 2500, "balanced": 7000, "deep": 20000 } } (characters). Ranking is deterministic matching; the agent reads the cited lines before relying on a result.
  • Auto Mode: implement PBI 305912 in Auto Mode runs the whole PBI inside the scope you authorize (recorded in plan section 0). It stops for business ambiguity, destructive or production actions, permission or credential changes, new dependencies, and anything outside the scope. G8, the command guard, and the IDE's own confirmation prompts still apply.
  • Upgrading from 3.3.0: run Install / Upgrade. Each repository is authorized once (the agent asks); the old index is rebuilt on first use; tasks, repos.json, and notes are kept. Roll back by installing the previous zip over this one; replaced files are in %USERPROFILE%\.akzo-agent\backups\.
  • Release packages contain release-manifest.json; the installer refuses a package with a changed, missing, or unlisted file. Compare the zip's SHA-256 with the value you received from the publisher (Get-FileHash <zip> -Algorithm SHA256). The hash proves the file is unchanged; it does not show who built or approved it.

SonarQube and code rules

The agent holds changed code to the project's Sonar quality gate and rules (agent section 6a). It uses the strongest source available and names it in the plan's Sonar table:

  1. SonarQube MCP tools in Copilot Chat, when you have added a SonarQube MCP server to the IDE.
  2. Read-only server queries through the helper (quality gate, issues, hotspots, coverage, duplication, rule details), when the repository has a project key and a server is reachable with a token.
  3. Sonar analyzers in the build or lint run (for example a Sonar analyzer package for C#, or the Sonar ESLint plugin), when the repository references them.
  4. SonarQube for IDE diagnostics in the problems list, when the extension is installed.
  5. Otherwise a static review against the agent's code rules, reported as "not a Sonar analysis".

Server queries: the project key comes from sonar-project.properties (sonar.projectKey) or the pipeline's Sonar step. Set the server and a personal token as user environment variables, then restart the IDE so Copilot's terminal sees them:

[Environment]::SetEnvironmentVariable('SONAR_HOST_URL', 'https://sonarqube.example.com', 'User')   # SonarQube Cloud: https://sonarcloud.io (default when sonar.organization is set)
[Environment]::SetEnvironmentVariable('SONAR_TOKEN', '<your token>', 'User')

The server must use https (a loopback address such as localhost is exempt, for local testing); the helper refuses plain http to any other host before sending anything (INSECURE_HOST) and never follows a redirect. The host must also be allowed by the policy or your recorded authorization (HOST_NOT_ALLOWED). The helper reads the token itself and sends it only in the request header, so it never appears in chat or on a command line. The agent never asks for, prints, or stores a token. Check what was detected:

powershell -NoProfile -ExecutionPolicy Bypass -File "$env:USERPROFILE\.akzo-agent\modules\investigate\scripts\akzo.ps1" sonar -Repo <repo-id>
powershell -NoProfile -ExecutionPolicy Bypass -File "$env:USERPROFILE\.akzo-agent\modules\investigate\scripts\akzo.ps1" sonar -Repo <repo-id> -Check gate

Gate for new code: the project's gate from the server. Without a server the agent uses defaults and says so: 0 new issues, every new security hotspot listed for your review, changed-line coverage of at least 80%, and duplicated lines in new code of at most 3%. Coverage of changed lines comes from the repository's own coverage tool (Cobertura or LCOV reports written to the task's evidence folder) and the helper's coverage command.

Server results describe the last analysis uploaded for the branch, not your uncommitted edits; the agent uses them for the baseline, thresholds, and rule details. It never uploads an analysis (scanner run) unless you ask, never adds suppressions, // NOSONAR, or exclusions, and asks before adding an analyzer package.

Quick start: Start Development

  1. In Copilot Chat select akzo-master-sdd and send: 
    Start Development
  2. A Windows file dialog opens (look behind the IDE window if you do not see it). Choose the refined PBI: .md, .txt, or .docx; .pdf needs pdftotext (Poppler) on PATH. The file is converted to %USERPROFILE%\.akzo-agent\inbox\<file name>\refined-pbi.md; the original is kept under source\ and never changed.
  3. A second dialog opens: select any number of supporting documents at once (Ctrl+click), or Cancel for none. They are copied to supporting\ beside the PBI; your originals are never changed, duplicates are detected, and a second file with the same name is kept as name-2. Readable: Markdown, text, JSON, YAML, XML, CSV, code, .docx, .xlsx, .pdf (with pdftotext); images and other formats are listed but not read.
  4. The agent reads the PBI number and title from the document and picks the repository (the open workspace, or the only one registered). When all three are clear it starts at once; otherwise it asks one question batch with the answers pre-selected.
  5. It copies everything to <tasks>\<repo-id>\<PBI number>\, uses the repository's architecture index, and maps every requirement to existing code (EXISTING / REUSABLE / EXTEND / NEW / UNKNOWN). It then stops three times for your approval: after the gap map, after spec.md, and after plan.md (in the repository's spec folder as <TitleInPascalCase>\, or beside the PBI). Each stop is shown by name with what you are deciding, and you choose Approve, Request changes, or Custom response (typing approve or approve all still works; see Gates and progress). After plan approval it implements test first, builds, tests, runs analyzers/Sonar, fixes, and reports.

Without the chat command: double-click Start-Development.cmd (the same two dialogs), then type start in Copilot Chat (it is on the clipboard). You can also drop files or folders (PBI plus notes) in the inbox yourself and type start. Add documents to a running task with attach <files> to <PBI>; type develop <PBI> end to end to run without the approval stops.

Approval limits: the gates are enforced by the agent's instructions and the statuses recorded in spec.md and plan.md. Copilot offers no hook that blocks file edits, so the IDE cannot technically stop a model error or an explicit instruction from skipping a gate.

The agent states its version in its first reply. install.ps1 -Verify shows the installed version and the version in your Akzo-Agent folder.

  • Choices at a stop: Approve (continue), Request changes (the stage is revised and shown again), Custom response (a question or another instruction; nothing is approved). Where the IDE offers clickable options (VS Code askQuestions) they appear as buttons; otherwise as numbered options. "ok", "thanks", or "continue" is never taken as approval.
  • Approval history: each decision is appended to <tasks>\<repo>\<PBI>\approvals.jsonl with the stop's name, your choice and words (secrets redacted), your user name, the time, and the SHA-256 of the document you decided on. A stop cannot be approved twice, before the stop before it, or after you asked for changes until the revised version is shown.
  • Task progress uses the task titles from plan.md and these statuses: Not Started, In Progress, Implemented - Verification Pending, Blocked, Verified (its build and tests ran and passed), Completed (the final checks passed). Plans written before 3.10.0 (todo / done) are read the same way. Stop names and explanations can be edited in modules\plan\assets\workflow.json.

Start a task from a refined PBI (manual)

Put each refined PBI in its own folder under the tasks folder. The folder names tell the agent the target repository and the PBI ID:

<tasks folder>\<repo-id>\<PBI-ID>\refined-pbi.md
  • Tasks folder: %USERPROFILE%\.akzo-agent\tasks by default. On the machine this guide was written on, that is C:\Users\lenovo\.akzo-agent\tasks. The installer prints the path; you can also print it with: 
    (powershell -NoProfile -ExecutionPolicy Bypass -File "$env:USERPROFILE\.akzo-agent\modules\investigate\scripts\akzo.ps1" home | ConvertFrom-Json).tasks
  • repo-id: an id from repos.json, for example backend-functions. Do not skip this folder level.
  • PBI-ID: letters, digits, ., _ or -, for example PBI-12345 or 305912.
  • File name: refined-pbi.md (letter case does not matter). Include the acceptance criteria and, if you have them, the implementation steps.
  • Other files in the same folder or its subfolders (request notes, decision log, open questions, evidence, handover documents) are read as supporting input. The agent never edits them; if they conflict with refined-pbi.md, the PBI wins and the conflict becomes a question.

What the agent does with it

  • Repository skills and instructions: it reads the ones in the target repository (root and one level down, e.g. src\.github\skills, .github\instructions, copilot-instructions.md, AGENTS.md) that match the task, follows them as the project's conventions, and lists them in spec §8.
  • Reference implementation: when the PBI or inputs say the behavior already exists (e.g. done for CDMS, now needed for DAB through GraphQL), it finds that code and its tests first, maps it file by file in spec §6 (same / adapted / not applicable), and mirrors it while keeping DAB/GraphQL semantics. For GraphQL it edits the .graphql documents and regenerates the client.
  • PBI steps: if refined-pbi.md lists implementation steps, the plan follows them in order and records any deviation.
  • Requirement check: missing inputs and contradicting acceptance criteria become questions before implementation.
  • Changes to the PBI: after the spec is written it saves refined-pbi.baseline.md. If you edit refined-pbi.md later, the next run diffs it, updates the affected spec and plan parts, and asks if finished code contradicts it.
  • Resume: existing spec.md and plan.md are never overwritten; plan §0 records where to continue.

The agent compares the current changes with 2-4 sibling features (naming, structure, GraphQL reuse, DI, error handling, tests), fixes confirmed deviations, builds, runs the tests, and reports what was fixed, verified, and left open.

How accuracy is enforced

  • Sibling features first: before the spec, the agent reads the closest existing features end to end and fills a conventions table (folders, namespaces, commands/queries/handlers/validators, services, DTOs, constants, resource keys, GraphQL operations and generated types, DI, tests). Every new name in the plan cites the sibling it copies.
  • GraphQL reuse: existing queries and mutations are searched and reused before new ones are added; the client is regenerated with the repository's command and the generated types are checked.
  • Integration check: before handover, new files must be referenced, registered in DI, reached from their endpoint, and free of new nullable or analyzer warnings; sibling feature tests are run when shared code changed.
  • No invented rules: unclear business decisions are listed and asked once; everything that does not depend on them is built.
  • Continuous: once implementation starts, the agent keeps going task by task until handover; failures are fixed, not reported as a stopping point.

Questions you will get

Only questions that change behavior, a contract, data, or the target repository, or that come from a missing or contradictory requirement. They arrive once per phase, in one batch, each with options and a recommended answer (in VS Code through the askQuestions picker). Pick the answers and the agent continues; it does not ask per file, per step, or "shall I continue?".

Where the results appear

  • Code changes: in the target repository, visible in Git Changes / Source Control, uncommitted.
  • Spec and plan: <repo>\<specsDir>\<Feature>\ when specsDir is set, else the task folder.
  • Progress: plan.md §0 (start state, remaining) and §2 (task status).
  • Validation results: plan.md §4 and §6 (command, result, counts), with logs and coverage reports in the task's evidence\ folder. The final handover in chat lists the same paths.

Permissions

Copilot asks before an agent reads or edits files outside your workspace and before it runs terminal commands. The agent keeps these to a minimum: the workflow is inside the agent file (no workflow files to read), and one helper call starts or resumes a task.

VS Code: one-time setup

powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\install.ps1 -ConfigureVSCode

Adds a marked block at the top of your VS Code user settings.json (backed up first, kept up to date on reruns, removed by -Uninstall; your comments and other settings are left as they are):

  • chat.tools.terminal.autoApprove: one rule that approves only powershell -NoProfile -ExecutionPolicy Bypass -File "<your profile>/.akzo-agent/modules/investigate/scripts/akzo.ps1" <command> .... Command lines with ;, |, &, $, backticks, or redirection, and any other script, still ask.
  • github.copilot.chat.additionalReadAccessPaths: %USERPROFILE%\.akzo-agent and the tasks folder, so the refined PBI and inputs are read without asking. This applies to every Copilot agent, read-only.
  • chat.agent.maxRequests: 400. VS Code otherwise pauses any agent with Continue to iterate? after 50 requests (default confirmed in VS Code 1.142.0), which interrupts a full implementation. This is a limit for all agents, not a behavior change.

If either setting already exists in your settings.json, the installer leaves it alone and prints a warning; merge the entry yourself.

What appears in Git Changes

  • Installing, updating, uninstalling: nothing in any target repository. The installer compares HEAD and git status of every registered repository before and after, and fails if anything changed.
  • Planning without specsDir: nothing. refined-pbi.md, inputs, spec, plan, and evidence live in the tasks folder. The helper refuses a task folder inside a Git repository.
  • With specsDir: a new untracked <specsDir>\<Feature>\ folder with spec.md and plan.md, meant to be committed.
  • Repo mode: a new untracked specs\<PBI-ID>\ folder with spec.md and plan.md.
  • Implementation: every edited file shows as modified or added, including regenerated GraphQL clients. Nothing is hidden with ignore rules, skip-worktree, or assume-unchanged.
  • Your own uncommitted work stays as it was; the agent records it before editing and never stashes, resets, or reverts it.
  • The agent does not commit, push, merge, or deploy unless you ask.
  • Changes to the agent itself appear only in the Akzo-Agent repository.

Update and uninstall

Update

Get the latest Akzo-Agent files, then double-click Install-MasterAgent.cmd > Install / Upgrade (or re-run the installer). Unchanged files are skipped; replaced and removed files are backed up. Upgrading keeps repos.json, authorizations, tasks, repository memory, and profiles-custom. From 3.6.0 to 3.7.0 nothing needs re-authorizing or re-indexing. The first call per repository builds the profile cache. If you customized a profile file, compare it with the shipped 3.7.0 version (new sections in the shared skills and the DAB/CDMS architecture skills).

powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\install.ps1

Uninstall

Double-click Uninstall-MasterAgent.cmd and confirm, or use the commands below. Removes the agent files, helper, and templates recorded in the install manifest (backing up any you edited) and the VS Code settings block added by -ConfigureVSCode. Keeps repos.json, tasks, maps, graphs, and backups.

powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\install.ps1 -Uninstall -DryRun
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\install.ps1 -Uninstall

Self-test (maintainers)

powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\test.ps1

Runs in a temporary profile and checks that your real profile is untouched. scripts\test-gui.ps1 drives the real file dialog, setup window, and uninstall confirmation through the .cmd launchers (needs a desktop session).
