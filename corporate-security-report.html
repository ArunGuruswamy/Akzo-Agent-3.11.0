5. Commands and external tools

External tools used by the package: Windows PowerShell 5.1 and .NET (Windows Forms for dialogs, ZIP and XML for Word/Excel reading, ACL APIs for folder permissions, Authenticode status), Git; optional: pdftotext, Python with graphify, SonarQube/SonarCloud Web API (read-only GET), SonarQube MCP server and IDE extension (if the developer has them). The package downloads nothing and installs nothing.

Command guard (guard), run by the agent before every non-helper terminal command:

  • BLOCK (never run; no approval releases it): external transfer (copy tools, uploads, mail, cloud storage, new Git remotes), remote code execution and piping downloads into a shell, tampering with security services or firewall, execution-policy changes, registry and policy edits, elevation, credential-store access.
  • NEEDS_APPROVAL: commit, push, merge and similar Git actions; dependency installs; database migrations; recursive deletes and destructive Git; deployments; Sonar analysis uploads; other network commands.
  • ALLOW: the helper itself (exact form) and other commands that match no rule, such as build, test, and read-only commands.

The deny rules work by category and behaviour. They were rewritten after endpoint protection objected to a version that spelled out attack-tool names (see "Endpoint protection findings").

Scripts started with -ExecutionPolicy Bypass: the launchers, the installer's child processes, and the VS Code auto-approve rule (which approves only the exact helper command line). The switch applies to that one process and does not change any policy, but it is a bypass of the machine's execution policy and needs security review; where Group Policy enforces signed scripts it will not work at all.

Endpoint protection (Windows Defender) findings during development

  1. Helper blocked by the antimalware scan interface. After a version of the command guard listed well-known credential-theft utility names as plain strings, Windows blocked the entire helper script when it was loaded ("This script contains malicious content and has been blocked by your antivirus software"). The helper, installer-driven discovery, and tests could not run until it was fixed. Remediation: the names were removed; the credential-access rule now matches behaviours (credential-manager utilities, secure-string and certificate export, credential-store files). No encoding, splitting, obfuscation, exclusion, or change to Defender settings was used, and a comment in the code records why the rules are written this way.
  2. Test script blocked once. A test case that named the command used to stop the antivirus service was flagged when the test script was loaded. The case was removed; the security-tampering category remains covered by a firewall-tampering case.
  3. Disclosure of investigation steps. To find which test string was flagged, fifteen throwaway one-line scripts (each holding one test string as inert text) were created and run in the session's scratch folder; one was flagged. The files were deleted afterwards. Nothing in Defender's configuration was changed. Probing stopped when instructed.
Implication for deployment: the package contains deny-lists and adversarial test strings as data. Managed endpoints may flag scripts or the test suite. Do not disable protection or add exclusions to work around it; give the security team the package, its hashes, and this report, and let them decide on allow-listing by publisher or hash. Only the agent file, the helper, the templates, and the version file are installed (six files); the test suite stays in the package.

10. Detected violations and unresolved risks

  • Intermittent test failure, cause not established. One full run of the suite after the G8 changes failed three checks, all about policy handling for the 'ui' fixture repository (policy blocking, restricted classification, approved-model check). The output did not include the compared values, so the cause was not established. In the more than 20 full runs since, the same three checks passed every time (in two of those runs other checks failed because of mistakes in newly written tests, which were corrected), and the suite now prints the compared values when a check fails. No code change was made for it because no cause was identified. Untested hypothesis: interference from another process with freshly written temporary files. Treat the suite as having an unexplained intermittent failure until it recurs with the diagnostics in place. Separately, one full run on 2026-10-26 took 5,938 seconds instead of the usual 300 to 400; the cause was not identified (a timed rerun took 355 seconds), and the suite now reports every step that takes 15 seconds or more.
  • The developer's authorization is not technically protected (see "Security defects found and fixed", known limitation). Enforcement of approval needs the administrator policy.
  • The command guard and the G8 command log depend on the agent calling guard: Copilot offers no hook that forces it. A missing log is reported as NOT VERIFIED, but a command run without the guard leaves no trace in it.
  • Secret, suppression, and dependency detection is pattern-based and can miss or over-report.
  • Memory is protected by file permissions only (no encryption); administrators and backup software can read it. Retention applies to facts, not to logs, task folders, or reports.
  • Symbol extraction uses regular expressions; ranking is deterministic matching, not proof. The agent is told to read the cited lines.
  • Scripts are not code-signed. SHA-256 hashes (release manifest, install manifest) show a package is unchanged since it was built; they do not show who built or approved it.
  • 3.4.1 is slower per helper call than 3.3.0 (interleaved medians on a 663-file repository: warm +23%, cold +83%), the cost of content fingerprinting and the G8 checks. It is about 10% faster cold and 19% faster warm than 3.4.0 with every check kept; an earlier estimate of "a third" was withdrawn because it compared runs taken under different machine load. The overhead looks mostly like a fixed per-call cost: on a 2-file repository (one round, indicative only) 3.4.1 was still about 33% to 39% slower than 3.3.0. Deferred for lack of a safe, worthwhile gain: one combined git call for fingerprinting, lazy symbol extraction, a background indexer, a real parser.
